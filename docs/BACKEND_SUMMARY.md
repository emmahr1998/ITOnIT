# ITOnIT Backend — Quick Summary (5–10 minute read)

For full detail, see `BACKEND_ARCHITECTURE.md` (deep dive), `BACKEND_API_GUIDE.md`
(endpoint reference), `BACKEND_DIAGRAMS.md` (visuals), `BACKEND_FLOW.md` (worked example),
and `PROFESSOR_QA.md` (Q&A). This file is the one to read right before presenting.

## What it is

A REST API (no server-rendered pages) for an internal IT support ticket system. Employees
report issues; technicians resolve them; managers assign and oversee; administrators manage
users and accounts. Every action is authenticated, permission-checked, and — for tickets —
audited.

## Stack

Python, **FastAPI** (routing, validation, auto-generated Swagger), **SQLAlchemy 2.0** (ORM),
**pyodbc** (SQL Server driver), **Alembic** (migrations), **Pydantic v2** (request/response
validation), **PyJWT** (access + refresh tokens), **pwdlib/Argon2** (password hashing),
**python-multipart** (file uploads), **pytest** (280 tests, all passing).

## Architecture in one picture

```
Client → FastAPI route → auth/role dependencies → Pydantic validation
       → Service (business rules) → Repository (SQL) → SQL Server
       → response schema → JSON
```

Five layers, one direction of dependency: **routes** are thin and only translate HTTP ↔
domain exceptions; **services** own business rules and transactions; **repositories** are the
only place SQL queries are built; **models** are the tables; **schemas** are what actually
crosses the wire. This separation is why, for example, a password hash can never leak in a
response — no response schema anywhere declares that field.

## Database (10 domain tables + Alembic's own bookkeeping table)

`roles`, `departments`, `priorities`, `locations`, `categories`, `users`, `tickets`,
`comments`, `attachments`, `ticket_history`. Every foreign key and unique constraint is
enforced at the database level (confirmed live against the running SQL Server instance).
Ticket cascade deletes (comments/attachments/history) are enforced at the **application**
level (SQLAlchemy ORM `cascade="all, delete-orphan"`), not as `ON DELETE CASCADE` at the
database level — correct for everything the app does, but worth knowing if asked. No
foreign-key column has an index yet (confirmed live) — the top database improvement to make
before real production data volume.

## Authentication in one paragraph

Login with username (or email) + password → backend verifies the Argon2 password hash and
that the account is active → issues a short-lived **access token** (30 min) and a
long-lived **refresh token** (7 days), each a signed JWT carrying a `"type"` claim so one
can never be used in place of the other. Every subsequent request sends the access token as
`Authorization: Bearer ...`; when it expires, `POST /auth/refresh` exchanges the refresh
token for a new access token without re-entering credentials.

## Roles, at a glance

| Role | Can do |
|---|---|
| Employee | Create/view own tickets, comment/attach on own tickets, edit own ticket only while still NEW |
| Technician | View/edit/comment/attach on assigned tickets, change status of assigned tickets |
| Manager | Everything a Technician can on *any* ticket, plus assign technicians, plus manage Categories/Departments/Priorities, plus view all users |
| Administrator | Everything a Manager can, plus create users, edit any user's any field, reset any password, plus manage Locations |

Notably: a Manager can *see* every ticket and every user, but cannot edit another user's
account or manage Locations — only an Administrator can do either.

## Ticket lifecycle

`NEW → ASSIGNED → IN_PROGRESS ⇄ WAITING_FOR_EMPLOYEE → RESOLVED → CLOSED`. `CLOSED` is
terminal — the code does not support reopening. Assignment auto-advances `NEW → ASSIGNED`;
every other transition goes through `PATCH /tickets/{id}/status` and is checked against a
fixed transition table. `resolved_at`/`closed_at` are set automatically on entering those two
statuses.

## Ticket numbers

Format `IT-<year>-<6-digit sequence>`, e.g. `IT-2026-000001` — generated by counting
existing tickets for the current year and incrementing. A retry loop handles the rare case of
two requests generating the same number at the same instant.

## History / auditing

Every meaningful ticket change — creation, field edits, assignment, status changes, comments
added/edited/deleted, attachments added/deleted — writes one row to `ticket_history` with the
old value, the new value, who did it, and when. One shared function
(`HistoryService.record`) is the only place these rows are ever created.

## Attachments

Uploaded as multipart form data, validated (non-empty, ≤10 MB, extension allow-listed), saved
to disk under `storage/attachments/` with a random server-generated filename (never the
original), with only metadata (not the file bytes) stored in SQL Server. An attachment
belongs to exactly one ticket (no longer optionally to a comment too — that FK was removed
as unused). Deleting a ticket now also deletes its attachments' physical files, not just the
database rows.

## Locations

A predefined, admin-managed list (like Departments/Priorities) that replaced free-text
ticket locations. Deactivated rather than deleted (`is_active=False`) so historical tickets
keep a valid reference — and unlike `Category.is_active` (which is unused dead weight),
`Location.is_active` is actually enforced: a ticket can never newly select a deactivated
location. Only an **Administrator** (not Manager) can create/edit/deactivate locations.

## API shape

Endpoints added most recently (Departments, Priorities, Locations, Users, `POST /ticket-new`,
`GET /all-tickets`, `PATCH /tickets/{id}`) wrap their response as `{"data": ..., "msg":
...}`. Older endpoints (Categories, Comments, Attachments, History, Auth, and the individual
`GET /tickets/{id}` / assign / status routes) return the object/array directly — this
inconsistency is intentional (the wrapper wasn't retrofitted onto already-working endpoints),
not a bug.

## Testing approach

No test database — every service accepts its repository as a swappable constructor argument,
so tests inject in-memory fakes instead of hitting SQL Server. Authentication itself is
tested for real (real JWTs are created and verified); only persistence is faked. Real
filesystem behavior (path-traversal defense) is tested against a real temp directory in
`test_storage_service.py`. Correctness against the actual, migrated SQL Server schema is
verified separately, via `alembic check` and a manual smoke test.

## Security — what's solid vs. what's missing

**Solid:** Argon2 password hashing, signed JWTs with distinct access/refresh types,
centralized role checks, ownership checks, 100% ORM-built queries (no SQL injection surface),
file-upload validation, git-ignored secrets, inactive-user enforcement.

**Missing (expected for a university project, not yet production-ready):** HTTPS
enforcement, token revocation/logout, rate limiting, malware scanning on uploads, cloud file
storage, structured logging/monitoring, database indexes on foreign keys, and — notably —
**no CORS configuration at all**, which would need to be added before any browser-based
frontend (even in local dev) could call this API directly.

**Latest review pass:** found and fixed two real bugs (a missing eager-load causing an extra
query per ticket, and deleted tickets leaking their attachment files on disk forever) — both
covered by new regression tests. Everything else found was a judgment-call recommendation
(naming/duplication/`is_active` inconsistencies, missing indexes), reported but not silently
changed. See `BACKEND_ARCHITECTURE.md` §22 for the full list.

## Files to know cold before presenting

1. `app/main.py` — the whole app in 17 lines.
2. `app/api/router.py` — every route group in one place.
3. `app/dependencies/auth.py` — how authentication and role checks actually work.
4. `app/core/security.py` — JWT + password hashing.
5. `app/services/ticket_service.py` — the biggest, most important business-logic file
   (ownership, status workflow, ticket numbering).
6. `app/models/ticket.py` + `app/models/user.py` — the two most connected tables.
7. `app/db/database.py` — engine/session/Base.
8. `alembic/env.py` + the files in `alembic/versions/` — how schema changes are made
   safely, including two recent examples of a data-preserving column-to-FK migration
   (departments, then priorities/locations).
9. `tests/conftest.py` — how the whole test suite avoids needing a real database.
